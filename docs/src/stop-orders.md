# Стоп-заявки

Стоп-заявка лежит у брокера и ждет цены. Пока цена не дошла до заданной, на бирже ее нет. Когда дошла, брокер
выставляет обычную заявку, рыночную или лимитную.

Для стоп-заявок есть отдельный трейт **`StopOrderExecutor`**. Обычных заявок он не касается, а `reconcile` и
`active_orders` стоп-заявок не показывают. Он реализован у всех трех брокеров (`caps().supports_stop_orders`).

## Виды

| Вид (`StopOrderKind`) | Зачем | Когда срабатывает |
|---|---|---|
| `StopLoss` | защита позиции | продажа - когда цена упала до `stop_price`, покупка - когда выросла |
| `TakeProfit` | фиксация прибыли | продажа - когда цена выросла до `stop_price`, покупка - когда упала |
| `StopLimit` | как `StopLoss`, но после срабатывания всегда лимитная заявка | как у `StopLoss`, `limit_price` обязателен |

Параметры (`PlaceStopOrderRequest`): `cid`, инструмент, сторона, вид, количество, `stop_price` (цена срабатывания),
`limit_price` (цена заявки после срабатывания: нет цены - рыночная), срок (`StopExpiry`: до отмены, до конца дня,
до даты). Номер `cid` - тот же UUID, что у обычных заявок, и правила те же: свой на каждую заявку, повторно не
отправляется, заранее записывается в журнал.

## Методы

| Метод | Что делает |
|---|---|
| `place_stop(req)` | ставит стоп-заявку, возвращает `OrderAck` с номером брокера |
| `cancel_stop(ref)` | снимает не сработавшую. `ref` - либо `StopOrderRef::Cid(cid)`, либо `StopOrderRef::Broker(номер)` |
| `active_stop_orders()` | список стоп-заявок, которые ждут срабатывания |
| `subscribe_stop_orders()` | поток статусов. **У всех трех брокеров `Unsupported`**: у БКС не подтверждено, что такие заявки приходят в канал статусов, у Т-Банка потока нет в API, у Финама отдельного потока нет |

Шлюз команд (`NotReconciled`, `Degraded`, `ShuttingDown`) действует на `place_stop` и `cancel_stop` так же, как на
`place` и `cancel`. Неясный ответ - `Unknown`, повтора нет. Подробности исходов: [Круг команд](orders.md).

Проверки без сети (нет цены у стоп-лимита, срок, которого нет у брокера, дробное число лотов) библиотека делает сама
до отправки, квота на них не тратится. Узнать о срабатывании стопа можно только опросом: нового события о нем нет.
Когда стоп сработал, брокер ставит обычную заявку, и ее ведет обычный поток заявок. Связь между стопом и
порожденной заявкой библиотека не строит.

## Пример

```rust
use brokapi::core::{
    ClientOrderId, Error, InstrumentId, PlaceStopOrderRequest, Price, Qty, Side, StopExpiry,
    StopOrderExecutor, StopOrderKind, StopOrderRef,
};

/// Ставит стоп-лосс на продажу, смотрит список ждущих и снимает стоп по номеру брокера.
async fn protect<U: StopOrderExecutor>(
    ud: &U,
    instrument: InstrumentId,
    qty: Qty,
    stop_price: Price,
) -> Result<(), Error> {
    let cid = ClientOrderId::new_v4();
    let ack = ud
        .place_stop(PlaceStopOrderRequest {
            cid,
            instrument,
            side: Side::Sell,
            kind: StopOrderKind::StopLoss,
            qty,
            stop_price,
            limit_price: None, // рыночная заявка после срабатывания
            expiry: StopExpiry::GoodTillCancel,
        })
        .await?;
    // Номер брокера нужно сохранить: после рестарта у Т-Банка отмена по cid невозможна
    let broker_id = ack.broker_id;

    for stop in ud.active_stop_orders().await? {
        println!("стоп {:?} {:?} по {}, cid {:?}", stop.kind, stop.state, stop.stop_price, stop.cid);
    }

    ud.cancel_stop(StopOrderRef::Broker(broker_id)).await
}
```

## Что отличается у брокеров

| | БКС | Т-Банк | Финам |
|---|---|---|---|
| Как ставится | условная заявка (`orderType = 5`), синхронным методом | отдельный сервис стоп-заявок | стоп-лосс и стоп-лимит обычной заявкой типа стоп, тейк-профит отдельным методом SL/TP |
| Тейк-профит с ценой после срабатывания (`limit_price`) | да (лимитное исполнение), не проверено вживую | да | **нет**: у Финама там защитный спред, а не цена. Вернется `Rejected` с кодом `unsupported_limit_price` |
| Срок «до отмены» | да | да | да |
| Срок «до конца дня» | нет, `unsupported_expiry` | нет, `unsupported_expiry` | да |
| Срок «до даты» | нет, `unsupported_expiry` | да | только у тейк-профита |
| Количество | целое, не меньше 1 | целые лоты | число больше нуля, штуки |
| Свой `cid` в списке | находится одним запросом по номеру заявки, если брокер знает условные заявки (не проверено) | **только пока работает процесс, который поставил заявку.** Брокер `cid` не возвращает, связь хранится в памяти. После рестарта `cid` пустой | да, читается из комментария заявки |
| Поток статусов | нет | нет в API | нет |

Особенности:

- **БКС: срок жизни.** Документация срок условной заявки не называет. Поэтому БКС принимает только «до отмены» и
  никакого поля срока не шлет. Сколько заявка проживет на самом деле, покажет живой прогон (вопрос 12 в
  [Живых прогонах](live.md)). Направление срабатывания БКС выбирает сам из стороны и вида. Пару «стоп-лосс плюс
  тейк-профит» одной заявкой библиотека не создает. Чужую пару в списке показывает двумя заявками с одним номером.
- **Т-Банк: отмена после рестарта.** `cancel_stop(StopOrderRef::Cid(cid))` для стопа, поставленного раньше этого
  запуска, вернет `Rejected` с кодом `unknown_stop_order`. Снимайте по `StopOrderRef::Broker(номер)`: номер берите из
  журнала бота или из `active_stop_orders()`.
- **Финам: списки.** Стоп-заявки не попадают в `active_orders` и `reconcile`. Для них свой список.
- **Финам: процент вместо штук.** Если у чужой SL/TP-заявки единица объема - процент от позиции, в `qty` будет 0
  («не в штуках»), а не процент. Свои заявки библиотека ставит в штуках.
- **Т-Банк: длинный список.** Когда стоп-заявок слишком много для одного ответа (ошибка 30261), `active_stop_orders`
  читает список по периодам и склеивает. Если и так не вышло, `Rejected` с кодом `stop_orders_response_limit`. Подробно:
  [Т-Банк](brokers/tbank.md#стоп-заявки).
- **Т-Банк: лимит по инструменту.** Ответ 80007 (максимум стоп-заявок по инструменту) - это `Rejected` с кодом
  `stop_orders_limit`, а не `RateLimited`: повтор не поможет, снимите одну из заявок.
- **Сверка и стопы.** `cid` стоп-заявок в список для `reconcile` не кладите: обычной сверкой они не видны. После
  старта читайте `active_stop_orders()`.

Все это проверено на имитации всех трех брокеров, **вживую стоп-заявки не пробовались**. Вопросы, на которые должен
ответить живой прогон, собраны в [Живых прогонах](live.md).
