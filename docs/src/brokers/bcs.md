# БКС

Крейты: `brokapi-bcs-protocol` (REST и WebSocket клиент) и `brokapi-bcs` (коннекторы). **Живой проверки коннекторов не было.**
Вживую проверялся только нижний слой `brokapi-bcs-protocol`, и то по прежним методам заявок.

## Вход

| Что | Как |
|---|---|
| Токен | refresh-токен БКС (`BCS_REFRESH_TOKEN`). Из него коннектор получает токен доступа. Счет определяет сам токен: **`account_id` в настройке нет** |
| Чтение и запись | токены бывают на чтение и на запись. Для торговли нужен токен на запись и `BCS_IS_WRITE=true` (в коде `BcsConfig::with_write(true)`). Без этого брокер торговые команды не примет |
| Песочница | нет. Торговля идет на настоящем счете |
| Обновление | токен доступа обновляется после ответа 401, запрос повторяется один раз. Подробно: [Токены](../streams.md#токены-и-их-обновление) |
| Лимиты | `brokapi::bcs::limits::default_limits()`: встроенный файл `configs/bcs_limits.toml`, как у Т-Банка и Финама. Свой файл: `limits_from_toml_str` и `limits_from_toml_path`. Числа осторожные: брокер своих цифр не публикует |

## Идентификатор инструмента

`NativeId::TickerClass { ticker, class_code }`, например `SBER` и `TQBR`. Ключ библиотеки - `SBER@TQBR`. Любой другой
вид идентификатора даст ошибку настройки (`Config`): справочник для БКС не нужен, идентификатор собирается сам без
сети. Расписание торгов у БКС по инструменту: в `schedule` передается `"SBER@TQBR"`, иначе `Config`.

## Единицы и стакан

| Что | Как |
|---|---|
| Числа | цены, количества и суммы читаются из JSON в `Decimal` по тексту ответа, `244.30` остается `244.30`. Не проверено вживую, что брокер шлет их именно так |
| Количество | целое число, как в API БКС. Штуки это или лоты, **не подтверждено**: коннектор передает число как есть. Заявка с дробным количеством округляется |
| Глубина стакана | до 20. Больший запрос молча режется до 20 |
| Стакан | полный снимок. Поток идет по WebSocket, снимок по REST |
| Котировки | отдельный поток WebSocket |
| Свечи | таймфреймы M1 M5 M15 M30 H1 H4 D W MN. `D1` и `W1` библиотека шлет как `D` и `W`. **10-минуток нет**, `Unsupported` |
| Лента сделок | `last_trades` отдает сделки текущей торговой сессии, оставляя новейшие `limit` штук |

## Как устроены команды

БКС работает **синхронными методами**: `POST /orders/sync`, `/orders/cancel/sync`, `/orders/edit/sync`. Они ждут
решения брокера и отвечают состоянием заявки. Из этого следует:

- Отказ известен сразу как `Rejected`, а не через минуту из потока. Отказ может прийти кодом HTTP 4xx или внутри
  ответа 200 со статусом заявки 8 и причиной. Оба случая дают `Rejected`.
- В `OrderAck` приходит настоящий номер брокера (`orderId`), тот же, что в списке заявок и в потоке.
- Отмена объявляется успешной, только если брокер ответил, что заявка отменена. Заявка исполнилась раньше -
  `Rejected { already_filled }`. Ответ оставил заявку живой - `Unknown`.
- Прежние формы запросов (с номером заявки в пути) коннектор не вызывает. Они остались в `brokapi-bcs-protocol` и доступны
  через `raw()`.

## Как `cid` уходит к брокеру

В поле `clientOrderId` как UUID с дефисами. Обратимо. В **списке** активных заявок БКС поля `clientOrderId` нет, только
номер брокера. Поэтому `active_orders` и `reconcile` определяют `cid` так: по тому, что процесс видел сам, иначе
**одним запросом на каждую неизвестную заявку** (по ее номеру), иначе дают заявке подставной `cid`. Если на счете много
чужих заявок, сверка тратит много запросов, учитывайте квоту.

Порядок как у Т-Банка и Финама: шлюз команд, проверка входа, квота и только потом `cid` помечается использованным.
Поэтому после `RateLimited` (и после ошибки входа вроде `missing_price`) тот же `cid` годен: заявка никуда не ушла. То же для
`place_stop`. Общее правило: [Круг команд](../orders.md).

## Изменение заявки

Есть: `POST /orders/edit/sync`, брокер снимает исходную заявку и ставит новую под новым `cid`. Количество и цена,
которых вы не указали, берутся от исходной (один запрос). Если заявка исполнена частично, количество нужно указать
явно, иначе `Rejected { qty_required }`.

## Свои сделки, портфель

| Что | Как |
|---|---|
| Поток исполнений | из единого канала статусов `orders/events/ws`: сообщения с `lastQuantity > 0`, каждый `executionId` один раз. Режим `Lossless` |
| История | `POST /trades/search`. Запись плоская, **без `cid` и без комиссии** (`cid` пуст, комиссия 0) |
| Портфель | снимок REST. Поток по WebSocket. Деньги и позиции берутся из одного ответа |
| Список активных заявок | `POST /orders/search`, только заявки с 26 января 2026 года и не больше 1000 последних (ограничение документации) |

## Стоп-заявки

Условные заявки (`orderType = 5`). Принимается только срок «до отмены» (срок жизни условной заявки документация
не описывает), поле срока не отправляется. Направление срабатывания выбирает брокер. Пара «стоп-лосс плюс
тейк-профит» не создается. Потока статусов нет. Подробно: [Стоп-заявки](../stop-orders.md).

## Чего БКС не поддерживает или делает иначе

| Что | Как |
|---|---|
| Свечи 10 минут | `Unsupported("candles_m10")` |
| Справочник по виду: опционы и `Other` | `Unsupported`. Остальные виды работают, список читается **целиком**: страницами по 100, пока страница полная. Каждая страница тратит квоту, а список длиннее 200 страниц - ошибка, не обрезок |
| Поток стоп-заявок | `Unsupported` |
| Песочница | нет |
| Кадры между WebSocket и разбором | между сессией WebSocket и задачей разбора стоит канал на 512 кадров. Если он заполнится (задача разбора встала), кадр отбрасывается со счетчиком и записью в лог, **без** `Overflow`. Задача разбора ничего не ждет и опустошает канал сразу, поэтому на практике это недостижимо, под нагрузкой не проверялось |
| Перечитывание заявок после обрыва | нет |

## Лимиты

`configs/bcs_limits.toml`: общее ведро, рынок, заявки, отмена, справочные запросы. До 4 соединений. Цифры подобраны
осторожно и должны быть проверены на живом счете.

## Открытые вопросы на живой прогон

Полный список с пояснениями: [Живые прогоны](../live.md), раздел БКС. Главные:

1. Отвечает ли БКС на `GET /orders` по неизвестному `cid` именно `NOT_FOUND`. От этого зависит сверка.
2. Единицы количества: штуки или лоты.
3. Как ведут себя синхронные методы: сколько ждут, что в ответе, как выглядит отказ, повтор `clientOrderId`.
4. Присылает ли `orders/events/ws` сообщения без полей исполнения, заявки из приложения, условные заявки.
5. Срок жизни условной заявки, смысл поля `price`, номер брокера в ответе на условную заявку.
6. Что означает количество при `replace` частично исполненной заявки.
7. Что приходит в `orders/events/ws` после переподключения и нужна ли сверка после обрыва.
8. Совпадают ли числа лимитов с ответами сервера.
