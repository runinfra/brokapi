# Деньги, цены и количества

Цена, количество, лот, баланс и комиссия в библиотеке - точные десятичные числа. `f64` для них нигде не используется.
Страница объясняет, почему так, как создавать числа, как округлять цену до шага и что делает библиотека при переводе
форматов брокеров.

**Python.** Цена, количество и деньги - `decimal.Decimal`. В вызов можно передать `Decimal`, `int` или строку, `float` отвергается с `TypeError`. Округление до шага - `brokapi.round_to_step(цена, шаг, RoundMode.DOWN)`, правила те же, что у `round_to_step` в Rust. Время - `datetime` с часовым поясом.

## Три типа

| Тип | Что это | Где встречается |
|---|---|---|
| `Price` | цена одной бумаги | заявки, стакан, сделки, свечи, `stop_price`, `price_step` |
| `Qty` | количество, размер лота | заявки, исполнения, позиции, объем свечи, `lot_size`, `min_qty` |
| `Money` | сумма денег | баланс (`available`, `blocked`), комиссия, `price_step_value` |

Внутри у каждого `Decimal` (крейт `rust_decimal`): целое на 96 бит и до 28 знаков после запятой. Типы разные нарочно:
количество нельзя подставить вместо цены, а сумму в рублях вместо количества. Библиотека отдает `Decimal` и макрос `dec!`
из `brokapi_core`.

## Почему не `f64`

Брокеры присылают цены десятичными числами, и сетка биржи тоже десятичная. В двоичной дроби `244.3` не лежит ровно:

```rust
assert_ne!(0.1_f64 + 0.2, 0.3);          // 0.30000000000000004
assert_ne!(244.3_f64 % 0.01, 0.0);       // остаток 6.3e-15: цена «не на шаге»
assert_ne!((109.32_f64 / 0.01).fract(), 0.0); // 10931.999999999998 шагов
```

Для заявки это значит: цена, которая на бирже верная, у вас «не кратна шагу», а округление до шага уезжает на одну
копейку. Суммы портфеля набегают копейками. С `Decimal` те же числа точные: `0.1 + 0.2 == 0.3`, `244.3` кратно `0.01`.

Эталон, NautilusTrader, хранит цену, количество и деньги целыми числами с фиксированным масштабом. Мы взяли другое:
`Decimal` со своим масштабом у каждого числа. Брокеры дают разное число знаков (Т-Банк до девяти, БКС до восьми у цены,
Финам строку любой длины), и один общий масштаб либо режет цену, либо сужает диапазон. Скорость целых нам не нужна: это
слой подключения, а не движок, между числом и биржей сетевая задержка в миллисекунды.

## Как создать число

```rust
use brokapi::core::{Decimal, Price, Qty, dec};

let a = Price::new(dec!(250.15));            // из литерала
let b: Price = "250.15".parse()?;            // из текста: файл, форма, переменная окружения
let c = Price::from(250);                    // из целого
let d = Price::from_scaled(25015, 2);        // из мантиссы и числа знаков: 250.15
assert_eq!(a, b);

let lots = Qty::from(10);
let sum: Qty = [Qty::from(1), Qty::from(2)].into_iter().sum();
```

- Запятая не разделитель: `"12,5"` - ошибка разбора (`NumberError::Parse`).
- Числа сравниваются по значению: `Price` `244.30` равно `244.3`. А текст сохраняет запись: `244.30` печатается `244.30`.
- `Price * Decimal` дает `Price` (так считается «на 1% ниже»: `bid * Decimal::new(99, 2)`). Масштаб произведения больше: `244.30 * 0.99`
  печатается `241.8570`. После `round_to_step` до шага 0.01 значение `241.85`, а печать может быть `241.8500`: значение то же, масштаб записи
  не важен.
- Из `f64` число делается только явно и с округлением до заданного числа знаков: `Price::from_f64_lossy(244.3, 2)`.
  Имя говорит, что точность потеряна: `f64` уже принес двоичный шум, округление его только прячет. Обратно -
  `to_f64_lossy()`, для графика или строки лога, но не для цены заявки.
- В JSON число - строка: `"244.30"`. Так его не округлит ни один читатель.

## Как округлить до шага цены

Шаг цены и размер лота лежат в `TradingParams` ([Справочник API](api.md)). Округление точное, сетка начинается с нуля:

```rust
use brokapi::core::{Price, RoundMode, dec};

let step: Price = "0.05".parse()?;
let p: Price = "101.03".parse()?;
assert_eq!(p.round_to_step(step, RoundMode::Down)?, "101.00".parse()?);     // покупка: не дороже расчета
assert_eq!(p.round_to_step(step, RoundMode::Up)?, "101.05".parse()?);       // продажа: не дешевле расчета
assert_eq!(p.round_to_step(step, RoundMode::Nearest)?, "101.05".parse()?);  // ближайшая, половина - от нуля
assert!(p.round_to_step(step, RoundMode::Up)?.is_on_step(step));
```

Если параметры инструмента уже прочитаны (`trading_params`), короче так: `params.round_price(price, mode)` и
`params.round_qty(qty, mode)`. Нулевой или отрицательный шаг - ошибка `NumberError::StepNotPositive`.

## Проверка цены коннектором

Коннектор не знает шаг сам: он узнает его от вас. У каждого коннектора заявок есть `price_grid()`. Заполните его один раз
на инструмент:

```rust
let params = md.trading_params(&sber).await?;
ud.price_grid().learn(&params);
```

Дальше `place`, `replace` и `place_stop` проверяют цену заявки (и `stop_price`, `limit_price`). Цена не на шаге -
`Rejected` с кодом `price_off_step`, **до отправки**: квота не тратится, `cid` остается свободным. Если шаг инструменту
не передан, цена не проверяется, решает брокер. Таблицу можно задать и при создании: поле `price_grid` конфига
`UserDataConfig`, одну на несколько коннекторов (копии таблицы - один и тот же список).

Количество библиотека по-прежнему не сверяет с лотом: Т-Банк требует целое число лотов (`invalid_qty`), БКС округляет до
целого, Финам берет количество как есть. Размер лота и минимальное количество - в `TradingParams`.

## Как числа переводятся из формата брокера

Ни один путь не идет через `f64`. Что делает каждый коннектор:

| Брокер | Формат | В библиотеку | Из библиотеки |
|---|---|---|---|
| Т-Банк | `Quotation` и `MoneyValue`: целая часть `units` и миллиардные доли `nano`, у обеих частей знак числа | `units + nano / 10^9`, точно | на части: до 9 знаков, иначе `Rejected { invalid_price }`, молчаливого округления нет |
| Финам | `google.type.Decimal` (строка, допускает знак и порядок) и `google.type.Money` (`units`, `nanos`) | строка разбирается как есть | строка из числа без порядка, запись сохраняется: `244.30` уходит как `"244.30"` |
| БКС | числа JSON | сразу в `Decimal` из текста ответа (`serde_json` с `arbitrary_precision`) | JSON-числом с теми же знаками |

Что именно сохраняется: `244.30` не теряет нуль на конце, `0.0001` остается `0.0001`, число с 19 знаками не
обрезается. Это проверено тестами на всех трех форматах, в том числе случайными числами туда и обратно. То, что брокер
вживую шлет числа именно так, как в его документации, **не проверено вживую**.

Проценты в моделях БКС (доля в портфеле, доходность, изменение в процентах, ставка купона) остались `f64`: это
отношения, а не деньги, цены или количества. Деньги и цены в `brokapi-bcs-protocol` тоже `Decimal`.

## Что поменять в своем коде

Если бот уже писался под прежние типы, замените:

| Было | Стало |
|---|---|
| `Price::new(250.0)`, `Qty::new(10.0)` | `Price::new(dec!(250))` или `Price::from(250)`, `Qty::from(10)` |
| `price.value()`, `qty.value()` | `price.decimal()` (или печатайте число: `Display` есть) |
| `Qty(10.0)`, `price.0` | поле закрыто: `Qty::from(10)`, `price.decimal()` |
| `balance.available + balance.blocked` как `f64` | `Money` складывается и суммируется: `a + b`, `.sum()` |
| `lot_size: f64` и остальные поля `TradingParams` | `Qty`, `Qty`, `Price`, `Money` |
| округление до шага руками | `price.round_to_step(step, RoundMode::Down)` |
| `f64_to_quotation(...)` и `quotation_to_f64(...)` в `brokapi-tbank-protocol` | `decimal_to_quotation`, `quotation_to_decimal` |
| `precise_down(101.03, 0.05)` в `brokapi-bcs-protocol` | те же имена, аргументы и результат `Decimal` |
| функции Финама `dec`, `to_decimal`, `money` | возвращают `Decimal` и `Money` |

Подробности по дате - в [Изменениях](changelog.md).
