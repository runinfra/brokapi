# Запуск и обслуживание

Инструкции для того, кто держит службу `brokapi` постоянно: как запустить ее вместе с системой, что она делает при сбоях, как остановить гейтвей и снять заявки,
какие файлы где лежат и что делать, когда что-то не запускается. Первый запуск по шагам: [Быстрый старт](quickstart.md).

## Постоянный запуск (systemd)

`brokapi up` без `-d` работает на переднем плане и печатает, что запустилась: это ровно то, что нужно менеджеру служб. Когда systemd посылает `SIGTERM`, служба
останавливает гейтвеи (каждому дается `stop_timeout`, по умолчанию 10 секунд) и выходит.

Сначала пользователь службы, программа, конфиг и токены. Команды для Linux, из каталога, где лежат `brokapi`, `brokapi.toml` и `tokens.env`:

```sh
sudo useradd --system --no-create-home --shell /usr/sbin/nologin brokapi
sudo install -m 755 brokapi /usr/local/bin/brokapi
sudo install -d -m 750 -o root -g brokapi /etc/brokapi
sudo install -m 640 -o root -g brokapi brokapi.toml /etc/brokapi/brokapi.toml
sudo install -m 600 -o brokapi -g brokapi tokens.env /etc/brokapi/tokens.env
```

Конфиг и каталог `/etc/brokapi` принадлежат root, служба их только читает. Каталог состояния создаст systemd. Образец юнита `/etc/systemd/system/brokapi.service`:

```ini
[Unit]
Description=brokapi service
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=brokapi
ExecStart=/usr/local/bin/brokapi -c /etc/brokapi/brokapi.toml up
EnvironmentFile=/etc/brokapi/tokens.env
StateDirectory=brokapi
StateDirectoryMode=0700
UMask=0077
KillMode=process
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Запуск и первая проверка:

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now brokapi
sudo -u brokapi brokapi -c /etc/brokapi/brokapi.toml ps
```

В конфиге к этому юниту каталог состояния - тот, что создает systemd: `state_dir = "/var/lib/brokapi"`. Замечания к образцу:

- **`KillMode=process`.** Без него systemd при смерти службы убивает все процессы юнита, вместе с гейтвеями, и боты получают `Gap` с `NEW_EPOCH` на каждое падение
  службы. С ним гейтвеи переживают смерть службы, а служба, которую systemd запустил заново, подхватывает их (в журнале службы `taken over a running gateway`). `systemctl stop`
  и `systemctl restart` все равно останавливают гейтвеи: служба на `SIGTERM` останавливает их сама. Проверено на Linux временным юнитом `systemd-run`: без `KillMode=process`
  гейтвей умер вместе со службой, с ним остался тем же процессом и был подхвачен.
- **`StateDirectory=brokapi`, `StateDirectoryMode=0700` и `UMask=0077`.** systemd создает `/var/lib/brokapi` с владельцем из `User=`, а файлы службы получают права
  только для него. Без `state_dir` каталог состояния лег бы рядом с конфигом, в `/etc/brokapi`, куда служба от своего пользователя писать не может. В каталоге состояния
  ключи доступа ботов. Служба сама создает его с правами 700, но здесь каталог создает systemd, и без `StateDirectoryMode` он получит 755 (проверено временным юнитом).
- **Команды `brokapi` - от пользователя службы**: `sudo -u brokapi brokapi -c /etc/brokapi/brokapi.toml ps`. Каталог состояния закрыт для других пользователей, и команда
  от них отвечает `cannot read the state directory ...: it belongs to another user`. Так же бот: он должен работать от пользователя службы, чтобы прочитать `access.key`
  и открыть сокет гейтвея.
- **Токены** лежат в `/etc/brokapi/tokens.env` строками `TBANK_TOKEN=...` с правами 600 и владельцем из `User=`. В конфиге на них ссылается `token_env`. Либо
  `token_file` на файл с теми же правами.
- **`-c` с полным путем.** У юнита нет рабочего каталога с `brokapi.toml`.
- **Имя файла программы - `brokapi`.** Служба узнает свои гейтвеи по имени процесса. Программа под другим именем не подхватит гейтвей прежней службы.
- **`Restart=on-failure` следит только за самой службой.** Гейтвей в состоянии `failed` служба не перезапускает, и systemd о нем не узнает: за этим следит мониторинг, ниже.

Это образец, а не команда установки: подстройте пути и пользователя под себя. Установки службы одной командой пока нет, ни для systemd, ни для launchd на macOS и службы Windows.
На macOS и Windows службу можно запустить в фоне командой `brokapi up -d`, после перезагрузки машины ее придется запустить заново.

## Обновить программу

1. **Прочитайте [Изменения](../changelog.md)** между вашей версией и новой. Пока brokapi в альфе, формат каталога состояния может меняться, и об этом пишется там.
2. **Сделайте копию каталога состояния** (как - ниже).
3. **Подмените файл переименованием**, а не копированием поверх: `cp` поверх работающей программы на Linux падает с `Text file busy`.

   ```sh
   install -m 755 brokapi-<версия>-linux-x86_64/brokapi /usr/local/bin/brokapi.new
   mv /usr/local/bin/brokapi.new /usr/local/bin/brokapi
   ```

   Работающие процессы продолжают работать со старым файлом, пока их не перезапустят.
4. **Перезапустите службу**: `systemctl restart brokapi` или `brokapi down`, затем `brokapi up -d`. Гейтвеи остановятся и запустятся новой версией, каждый сверит журнал
   с брокером до приема команд. Боты получат `Gap` с причиной `NEW_EPOCH` и должны сверить заявки, как после любого перезапуска гейтвея ([События](events.md)).
   Заявки на бирже при этом не снимаются.
5. **Проверьте**: `brokapi --version`, `brokapi ps`.

## Копия и восстановление каталога состояния

Главное в каталоге состояния - журналы заявок `gateways/<гейтвей>/journal.jsonl` (какие заявки чьи и чем кончились) и ключи доступа `service.key` и `gateways/<гейтвей>/access.key`.
Копируйте каталог целиком.

- **Когда:** после `brokapi down` (или `systemctl stop brokapi`), перед обновлением и по расписанию. Копию работающей службы мы не проверяли.
- **Как хранить:** в копии ключи доступа к службе и гейтвеям. Храните ее как токен: права 600, не в репозитории и не в общей папке. Токенов брокеров в каталоге нет.
- **Как восстановить:** `brokapi down`, вернуть каталог на место, `brokapi up -d`. Гейтвей сверит журнал с брокером при старте.

Под systemd с юнитом выше, копия в архив с правами 600 и обратно:

```sh
sudo systemctl stop brokapi
sudo sh -c 'umask 077 && tar -C /var/lib -czf /root/brokapi-state-$(date +%F).tar.gz brokapi'
sudo systemctl start brokapi
```

```sh
sudo systemctl stop brokapi
sudo mv /var/lib/brokapi /var/lib/brokapi.old
sudo tar -C /var/lib -xzpf /root/brokapi-state-2026-10-26.tar.gz
sudo systemctl start brokapi
```

`umask 077` закрывает архив от других пользователей, `tar` от root при распаковке возвращает владельца и права (700 у каталогов, 600 у ключей). Без systemd то же
самое: `brokapi down`, `tar` каталога из `state_dir` вашего конфига, `brokapi up -d`.

**Если каталог состояния пропал**, служба не ругается: она молча начинает с пустым журналом и новыми ключами доступа. Заявки на бирже остаются, но гейтвей больше не знает,
какие из них поставили ваши боты: сверка бота покажет их как `foreign`. Ключ доступа ботов в `access.key` тоже будет новым.

## Мониторинг

`brokapi ps` отвечает кодом 0 при любых состояниях гейтвеев: код говорит, что команда выполнилась, а не что все здоровы. Для проверки есть `brokapi ps --check` (с версии 0.1.0-alpha.6).
Он печатает ту же таблицу и выходит с кодом 1, если хоть один гейтвей не в состоянии `running`, с кодом 3, если службы нет. Строка ошибки называет гейтвеи, которые не работают
(`not running: bcs-main failed`). Этого достаточно для cron и системы мониторинга:

```sh
brokapi -c /etc/brokapi/brokapi.toml ps --check >/dev/null || echo "brokapi: a gateway is down"
```

Проверка запускается от пользователя службы (cron этого пользователя или `sudo -u brokapi`): другому пользователю каталог состояния закрыт, и он получит код 1
с `cannot read the state directory`, а не состояние гейтвеев.

Гейтвей с `autostart = false`, который вы держите остановленным, `--check` тоже считает неработающим. Если нужна своя проверка, берите `brokapi ps --json`: это список гейтвеев,
у каждого `name`, `state` (`starting`, `running`, `restarting`, `stopping`, `stopped`, `failed`), `restarts`, `last_error` и `last_error_age_s` (сколько секунд назад).

Что еще стоит смотреть:

- **`restarts` растет** - гейтвей падает и поднимается. Причина в `brokapi logs <гейтвей>`.
- **`LIMIT` в `brokapi ps` близко к 100%** - боты упираются в лимит брокера, команды начнут получать `RateLimited`.
- **Место на диске** под каталогом состояния: там журналы гейтвеев и журналы заявок.

Метрик в формате Prometheus и адреса для проверки здоровья по HTTP у службы пока нет.

## Подключение по сети

На Linux и macOS гейтвей слушает только сокет Unix, на Windows - порт `127.0.0.1`, который выбирает сам. Настройки порта у гейтвея нет, и подключиться к нему с другой машины нельзя:
бот работает на той же машине, что и гейтвей. Несколько служб на одной машине различаются каталогами состояния, а не портами. Бот в контейнере на той же машине должен видеть
сокет гейтвея и его `access.key`. Мы это не проверяли.

## Несколько служб на одной машине

Каждый конфиг - своя служба: свой каталог состояния, свой сокет, свои гейтвеи. `brokapi -c prod.toml up -d` и `brokapi -c test.toml up -d` не мешают друг другу, а `brokapi services`
показывает обе:

```text
$ brokapi services
PID   GATEWAYS      UPTIME  CONFIG                      STATE DIRECTORY
4121  2/2 running   3h02m   /home/me/bots/prod.toml     /home/me/bots/prod.state
4377  1/1 running   12m07s  /home/me/bots/test.toml     /home/me/bots/test.state
```

Две службы на один каталог состояния не пустит ни одна: вторая откажется запускаться и назовет pid и конфиг первой. Так сделано, чтобы два процесса не делили
журнал заявок и сокеты. Если конфиги лежат рядом, у них разные имена файлов и значит разные каталоги по умолчанию (`prod.state`, `test.state`).

## Что происходит при сбоях

| Что случилось | Что делает программа | Что делать вам |
|---|---|---|
| Гейтвей упал или убит | Служба запускает его заново: сначала через 0,5 секунды, потом через 1, 2, 4 и так до 30 секунд. После 5 остановок за минуту гейтвей получает состояние `failed` и служба оставляет его в покое | Если `failed`: `brokapi logs <гейтвей>` покажет причину, после исправления `brokapi start <гейтвей>`. Боты получат `Gap` и сверятся: [События](events.md) |
| Служба умерла | Гейтвеи продолжают работать, боты ничего не замечают (под systemd - только с `KillMode=process`, см. выше). Новая служба (`brokapi up` с тем же конфигом) находит их по pid-файлам и сокетам и берет под присмотр | `brokapi up -d`. Гейтвей с именем `brokapi`, который не отвечает, будет убит: иначе он держал бы сокет |
| Машину перезагрузили | Ничего не работает, заявки на бирже остались | `brokapi up -d`. Гейтвей сверит журнал с брокером до приема команд. Боты получат `Gap` с причиной `NEW_EPOCH` |
| Гейтвей завис | Процесс жив, но не отвечает. `ps` показывает состояние `starting` у гейтвея, который уже работал (`UPTIME` не сбросился, `PID` тот же), и прочерки в колонках `BOTS`, `EVENTS/S`, `ORDERS`, `LIMIT` (с версии 0.1.0-alpha.6, раньше там оставались последние цифры). `ps --check` выходит с кодом 1. Ответит снова - вернется `running` | `brokapi restart <гейтвей>` |
| Токен перестал подходить | Гейтвей не может стартовать или переподключиться. Причина обычно видна в `LAST ERROR` команды `ps` и в строках `ERROR` журнала | Заменить токен, `brokapi restart <гейтвей>` |

## Остановить гейтвей и снять заявки

Заявка на бирже живет дольше, чем процесс, который ее поставил. Поэтому **остановка гейтвея заявок не снимает**: ни `stop`, ни `down`, ни перезагрузка. Снять их можно двумя способами.

| Команда | Что делает |
|---|---|
| `brokapi stop <гейтвей> --cancel-orders` | Сначала снимает активные и стоп-заявки счета, потом останавливает гейтвей. Если часть не снялась, команда перечисляет их и завершается с кодом 1 |
| `brokapi cancel-all <гейтвей>` | Только снимает заявки, гейтвей продолжает работать. Это аварийная кнопка, когда бот сошел с ума. На отказ по лимиту ждет и повторяет |

Остановка без снятия: `brokapi stop <гейтвей>` останавливает один гейтвей и держит его остановленным до `brokapi start`. `brokapi down` останавливает службу и все гейтвеи,
`brokapi down --leave-gateways` - только службу, гейтвеи остаются работать (следующий `up` подхватит их).

На Linux и macOS гейтвею посылается `SIGTERM`, и если он не вышел за `stop_timeout`, его завершают принудительно. На Windows у процесса без окна нет просьбы остановиться,
поэтому он завершается сразу, и в его журнале не будет строки `stopped`. Журнал и сверка при старте рассчитаны на внезапный конец, заявки это не теряет.

## Менять конфиг, не останавливая службу

Правьте `brokapi.toml` и применяйте:

- `brokapi reload` - привести работающие гейтвеи в соответствие с файлом: новые запустить, убранные остановить, измененные перезапустить, остальные не трогать.
- `brokapi add <гейтвей>` - запустить один гейтвей из файла. `brokapi remove <гейтвей>` - остановить и забыть его в памяти службы.

`remove` не правит файл. Пока гейтвей остается в файле, `reload` вернет его. Чтобы убрать насовсем, удалите раздел из `brokapi.toml`. Изменения `state_dir`, раздела `[service]` и `listen`
без перезапуска службы не применяются.

## Какие файлы где лежат

```text
brokapi.state/                  каталог состояния службы (state_dir)
  service.key                   ключ доступа к службе, права 600
  service.addr                  где служба слушает
  service.sock                  сокет службы (Linux, macOS)
  service.pid                   pid службы
  logs/service.log              журнал службы
  logs/<гейтвей>.log            журнал гейтвея
  gateways/<гейтвей>/           один гейтвей
    journal.jsonl               журнал заявок
    access.key                  ключ доступа ботов, права 600
    gateway.addr                где слушает гейтвей
    gateway.sock                сокет гейтвея (Linux, macOS)
    gateway.pid                 pid гейтвея
```

Путь до сокета Unix не может быть длиннее 107 байт на Linux и 103 на macOS. Каталог состояния в `~/Library/Application Support/...`
с длинным именем гейтвея легко получает путь длиннее. Тогда программа не отказывается стартовать: сокет кладется в личный каталог
`$XDG_RUNTIME_DIR/brokapi-<uid>` или `/tmp/brokapi-<uid>` (права 700, только ваш пользователь, чужой или подмененный каталог не берется),
а настоящий адрес записывается в `service.addr` и `gateway.addr`. Команды и боты читают адрес из этих файлов, так что ничего настраивать не нужно.
Сокет убирается, когда гейтвей или служба останавливаются. Если даже так не получилось, ошибка называет причину и предлагает короче `state_dir`
или свой короткий путь в `listen`. Если вы сами задали в `listen` слишком длинный путь, это тоже ошибка с пояснением: за вас его не меняют.

Журналы ротируются по размеру (`[service.logs]`): `max_size_mb` и `keep`. Каталог состояния **не кладите в репозиторий и в общую копию**: в нем ключи доступа к службе и гейтвеям.
Токены брокеров там не лежат, они только в переменной окружения или в `token_file`.

Реестр служб машины (его читает `brokapi services`) хранится отдельно: в `~/.local/state/brokapi/services` на Linux, на macOS и Windows в каталоге локальных данных пользователя.

## Если что-то пошло не так

| Что видно | Что значит | Что делать |
|---|---|---|
| `no config file found. Looked at: ...` (код 2) | Конфиг не найден | Указать `-c`, перейти в каталог с файлом или сделать `brokapi init` |
| `the environment variable ... (token_env) is not set` | В окружении службы нет переменной с токеном | Для systemd - `EnvironmentFile=`. В терминале - `export` перед `brokapi up` |
| `the state directory ... is used by another service (pid ..., config ...)` | Для этого каталога служба уже работает | `brokapi down` для нее или другой `state_dir` в этом конфиге |
| `a service already runs for ... (see brokapi services)` | `up -d` на уже запущенный конфиг | Ничего: служба работает |
| `no service is running for ...` (код 3) | Службы для этого конфига нет | Без systemd: `brokapi up -d`. Под systemd вторую службу не запускайте: `systemctl status brokapi` покажет, работает ли служба, и проверьте, что в команде тот же `-c`, что в юните |
| `cannot read the state directory ...: it belongs to another user` (код 1, с версии 0.1.0-alpha.6, раньше - `no service is running`) | Команда запущена не от пользователя службы, каталог состояния 700 | `sudo -u <пользователь из User=> brokapi -c ...` |
| `the gateway ... is starting: try again in a few seconds` или `is restarting` (код 4) | Служба запускает гейтвей, он еще сверяет журнал или ждет паузы перед перезапуском | Подождать, `brokapi ps` покажет `running`. Если `restarting` не проходит, причина в `Last error` |
| `the gateway ... is stopped` или `is failed: start it with brokapi start ...` (код 4) | Гейтвей остановлен, упал 5 раз за минуту или у него `autostart = false` | `brokapi logs <гейтвей>`, затем `brokapi start <гейтвей>` |
| `the service refused the access key` | Ключ в `service.key` не от этой службы | Команда ходит в тот же `state_dir`, что и служба? Проверьте `-c` |
| `the service ended at once (...)` и хвост журнала | Служба при `up -d` сразу вышла | Хвост журнала называет причину, чаще всего это конфиг |
| `... has mode 644: the access key must be readable by its owner only (chmod 600)` | У `access.key` чужие права, гейтвей с ним не стартует | `chmod 600` на файл |
| `the address ... is not on this machine: the gateway listens on loopback only` | В `listen` адрес не этой машины | Только `127.0.0.1` или сокет Unix |
| `another gateway is already listening at ...` | Тот же сокет занят живым гейтвеем | Это второй процесс того же гейтвея: `brokapi ps`, лишний остановить |
| У бота `the access key is missing or wrong` | Нет заголовка `authorization` или ключ не из `access.key` этого гейтвея | [Подключить бота](bots.md#что-нужно-знать-о-доступе) |
