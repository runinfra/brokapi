# Подключить бота

Как подключить бота к гейтвею: что нужно знать о доступе, в каком порядке вызывать, как жить с обрывами. Бот на Rust берет готовый клиент `RemoteClient`,
бот на Python берет тот же `Client`, что при прямом подключении к брокеру, бот на Go берет модуль `github.com/runinfra/brokapi/go`, бот на любом другом языке генерирует клиент из `.proto`. Гейтвей должен быть
запущен: [Быстрый старт](quickstart.md).

## Что нужно знать о доступе

Гейтвей слушает только эту машину и пускает только по ключу. Все, что нужно боту, лежит в каталоге гейтвея `<state_dir>/gateways/<имя>/`:

| Файл | Что в нем |
|---|---|
| `gateway.addr` | Где слушает гейтвей: `unix:/путь/gateway.sock` на Linux и macOS, `tcp:127.0.0.1:порт` на Windows. Служба пишет файл при запуске гейтвея |
| `access.key` | Ключ доступа. Права 600, читать его может только владелец. Менять не нужно: ключ создается один раз |
| `gateway.sock` | Сокет Unix. Если путь до него длиннее предела системы, сокет лежит в другом месте, а настоящий адрес всегда в `gateway.addr` |
| `journal.jsonl` | Журнал заявок гейтвея. Боту не нужен, не трогайте |

Каждый вызов несет два заголовка (metadata gRPC):

| Заголовок | Значение | Зачем |
|---|---|---|
| `authorization` | `Bearer <содержимое access.key>` | Без него или с чужим ключом - `UNAUTHENTICATED` |
| `x-brokapi-bot` | Имя бота: от 1 до 64 символов, буквы, цифры, `.`, `_`, `-` | Попадает в журнал гейтвея и в `brokapi status`. Нужно, чтобы фильтр `own_orders_only` знал, чьи заявки ваши. Без имени бот называется `anonymous` |

Имя придумываете вы. Два бота с одним именем гейтвей не различает: у них общие заявки в фильтре `own_orders_only`.

## Бот на Rust

Клиент `RemoteClient` лежит в крейте `brokapi-gateway`. Боту нужна только библиотека, без программы `brokapi`, поэтому зависимость берется с
`default-features = false`:

```bash
cargo add brokapi-gateway --no-default-features
```

Самая свежая версия, из репозитория: `cargo add --git https://github.com/runinfra/brokapi brokapi-gateway --no-default-features`.

`RemoteClient` умеет те же трейты ядра, что коннектор, поэтому код для прямого подключения почти не меняется: [Торговый бот на событиях, Rust](../rust/howto-trading-bot.md).
Отличия, с причинами: [Чем гейтвей отличается от прямого подключения](differences.md).

Порядок вызовов такой, и у каждого шага есть причина:

1. **Подключиться** по каталогу гейтвея и имени. Клиент сам читает адрес и ключ.
2. **Сверить** (`reconcile`) со своим списком заявок до любой торговой команды. Так требует контракт гейтвея, и причина та же, что в библиотеке: пока бот не знает, какие его заявки стоят у брокера, новая команда может задвоить заявку.
3. **Открыть поток событий** (`events`) и только потом подписаться. Подписка раньше потока теряет события из щели между ними.
4. **Торговать.** Перед `place` бот записывает `cid` в свой журнал, как при прямом подключении.

## Бот на Python

Пакет `brokapi` для Python (установка: [brokapi для Python](../python/index.md)) подключается к гейтвею тем же классом `Client`, что и к брокеру. Бот, который
уже работает с брокером напрямую, переезжает на гейтвей заменой одной строки. Остальные вызовы остаются прежними: `place`, `reconcile`, `order_book`, `raw`,
`async for envelope in client.events` и все остальные. Отдельного клиента gRPC на Python нет и не нужен: под `Client` лежит тот же код на Rust, что и в `RemoteClient`,
поэтому события, пропуски и сверка работают так же, как у бота на Rust.

```python

```

`"bcs-main"` - имя гейтвея в `brokapi.toml` (`[[gateway]]`, поле `name`). Каталог его состояния пакет находит сам: `<state_dir>/gateways/<имя>`. Если `state_dir`
не задан в конфиге, это `brokapi.state` рядом с `brokapi.toml`, туда и смотрит пакет, когда запущен в том же каталоге. Иначе укажите каталог состояния службы
аргументом `state=` или переменной окружения `BROKAPI_STATE`. Можно назвать сам каталог гейтвея: `dir=`.

`bot` - имя бота, как в заголовке `x-brokapi-bot`: от 1 до 64 символов, буквы, цифры, `.`, `_`, `-`. Оно обязательно: два бота с одним именем гейтвей не различает.
Остальные аргументы: `ready_timeout` (сколько секунд ждать гейтвей, который еще сверяет журнал, по умолчанию 30), `event_buffer` (сколько событий ждут читателя) и
`own_orders_only=True` (в потоке только события заявок этого бота).

Вы должны увидеть: `connect_gateway` вернул клиент, `client.gateway` называет гейтвей, а `client.broker` - его брокера. Ошибка `Config` с текстом `no gateway address in ...`
значит, что гейтвей не запущен или каталог не тот (`brokapi ps`). `Config` с текстом `refused the access` - ключ не тот (в каталоге лежит `access.key` другого гейтвея).
`Transport` с текстом `still starting` - гейтвей не успел сверить журнал за `ready_timeout`, причина в тексте.

Порядок вызовов тот же, что у бота на Rust: поток событий уже открыт (его открывает `connect_gateway`), поэтому сначала подписки, потом сверка, потом торговля.

### Что так же, что иначе

| | Через гейтвей |
|---|---|
| Методы `Client`: рынок, счет, заявки, стоп-заявки, история свечей, `raw` | Те же, с теми же типами и ошибками. `Decimal` для денег, `Unknown` для потерянного ответа на команду |
| Торговля до сверки | Закрыта: `place`, `cancel`, `replace`, `place_stop`, `cancel_stop` дают `NotReconciled` до первой успешной `reconcile`. Клиент отказывает сам, команда не уходит. Гейтвей этого не требует, правило то же, что у коннектора |
| Поток `client.events` | Тот же `async for`. В `source` стоят `<гейтвей>-md` и `<гейтвей>-ud`: соединение с брокером назвал гейтвей. После `close()` дочитывается то, что уже пришло, потом цикл кончается |
| Обрыв связи с гейтвеем, медленный бот (`Lagged`) | Клиент сам открывает поток заново и продолжает с номера последнего события. Если гейтвей жив и кольцо не обогнало, бот не замечает обрыва |
| Потеря событий | Новое событие `brokapi.Gap` в `client.events`. Что это и что делать - ниже |
| `client.limiter`, `limiter=` | Нет, `Unsupported`. Счетчик лимитов один на гейтвей, общий для всех его ботов, и живет не в вашем процессе |
| `close()` | Закрывает только соединение бота. Гейтвей работает, заявки на бирже стоят, подписки бота гейтвей отпустит через `bot_grace`. Отчетов остановки нет: список пустой |
| `raw()` | Работает так же, квота гейтвея. Метод со стримом отвергается, как и при прямом подключении |
| Запись событий (`brokapi.record`) | `record_events` пропускает `Gap` дальше, но в файл его не пишет: файл хранит события коннектора |
| Тесты | `mock.start_gateway()` в `brokapi.testing` поднимает гейтвей на имитации: [Тесты против имитаций](../python/testing.md#гейтвей-в-тесте) |

### Если потерялись события: `Gap`

`Gap` приходит как событие с полями `reason`, `requested_after`, `first_available`. Это то же, что `Overflow` и `Reconnected` у коннектора, и правило то же:
торговля закрыта (`Degraded`) до следующей `reconcile`, а поток продолжается с текущего места, переоткрывать ничего не нужно. Бот читает состояние счета
(`active_orders`, `order_state`, `executions`) и сверяется.

`reason` бывает трех видов, как у кадра `Gap` в [События и сверка после перезапуска](events.md):

- `"too_old"`: бота не было дольше, чем гейтвей хранит события. Подписки на месте.
- `"new_epoch"`: гейтвей перезапустили, это новый процесс. Подписок бота у него нет, `gap.subscriptions_lost` равно `True`: подпишитесь заново (номера подписок новые), потом сверьтесь.
- `"ahead"`: номер бота впереди гейтвея. Сверьтесь.

Подписки после `new_epoch` клиент сам не восстанавливает: набор подписок знает бот, и он же решает, какие из них еще нужны. Удобно собрать их в одну функцию и звать
ее и на старте, и на `Gap`, как `setup` в примере.

## Бот на Go

Готовый клиент - модуль `github.com/runinfra/brokapi/go`, каталог `go/` репозитория. В нем клиент, сгенерированный из `.proto` (пакет `gatewayv1`), и то, чего в `.proto`
нет: адрес из `gateway.addr`, ключ, два заголовка на каждом вызове, ожидание готовности гейтвея и ошибка библиотеки из ответа. `protoc` и плагины не нужны:

```sh
go get github.com/runinfra/brokapi/go@v{{brokapi_version}}
```

Номер модуля тот же, что у выпуска (тег `go/v{{brokapi_version}}`), `@main` берет самое новое. Он работает с программой `brokapi` с версии 0.1.0-alpha.6: раньше файлы `.proto` не собирались `protoc`. Нужен Go 1.25
или новее, его требует grpc-go.

`brokapi.Connect` читает адрес и ключ из каталога гейтвея и ждет, пока гейтвей ответит `Health = READY`. `conn.Gateway` - сгенерированный клиент, заголовки он шлет сам:

```go
conn, err := brokapi.Connect(ctx, brokapi.GatewayDir("brokapi.state", "bcs-main"), "my-bot")
if err != nil {
	log.Fatal(err)
}
defer conn.Close()
```

Вы должны увидеть: `err` равен `nil`. Текст `no gateway address in ...` значит, что гейтвей не запущен или каталог не тот (`brokapi ps`). `refused the access key` - в каталоге
`access.key` другого гейтвея. `is not ready` - гейтвей не успел сверить журнал за 30 секунд (`ConnectWith` с `ReadyTimeout` ждет дольше), причина в тексте.

С версии 0.1.0-alpha.10 `Connect` следит за изменением адреса до готовности гейтвея. Это нужно при перезапуске на Windows,
где новый процесс может слушать другой порт: подключение перейдет на него в пределах того же таймаута.

Порядок вызовов тот же, что у ботов на Rust и Python, только поток событий бот открывает сам: открыть `Events`, дождаться кадра `Ready`, подписаться, сверить, торговать.
Бот целиком, вместе с тем, как он переживает перезапуск гейтвея:

```go

```

```go

```


Ошибку библиотеки достает `brokapi.Detail(err)`: это `ErrorDetail` из заголовка `brokapi-error-bin`, решает его поле `Kind` (таблица в разделе [Ошибки](#ошибки)). `nil` значит,
что до библиотеки вызов не дошел: нет связи, чужой ключ, плохое имя бота. `status.Code(err)` из grpc-go работает на ошибке как обычно.

Пример запускается тестом против имитации БКС: бот ставит заявку, гейтвей убивают и запускают заново, бот подключается снова, получает `Gap` с причиной `REASON_NEW_EPOCH`,
подписывается и сверяется, заявку исполняют, и бот видит исполнение через новый процесс гейтвея. Тест - `crates/gateway/tests/go.rs`, весь бот - `go/examples/bot/main.go`.
Запуск на своем гейтвее из каталога `go` репозитория: `go run ./examples/bot -dir brokapi.state/gateways/bcs-main`. Без `BROKAPI_LIVE=1` бот только читает и останавливается
перед заявкой. **С `BROKAPI_LIVE=1` на настоящем счете заявка настоящая**: покупка одного лота по цене `-price` (по умолчанию 100.00), и бот ждет, пока она кончится.

## Бот на другом языке

Любой язык, в котором есть gRPC, подключается сам: контракт - файлы `.proto` в каталоге `crates/gateway/proto/` репозитория (они же лежат в пакете `brokapi-gateway` на crates.io), справочник
по ним - [Gateway (gRPC)](../api-gateway.md). Берите файлы той версии, что у вашей программы `brokapi`: каталог `crates/gateway/proto` в теге `v<версия>` на
`github.com/runinfra/brokapi`, например `v{{brokapi_version}}`. В `main` они могут быть новее выпуска. `protoc` и `buf` собирают эти файлы с версии 0.1.0-alpha.6, в более старых вызовы `Portfolio` и другие закрывают
одноименные типы и `protoc` отказывает.

Модуль для Go выше сделан именно так, и его код - образец для другого языка: `go/brokapi.go` в репозитории, две сотни строк. Что нужно сделать:

1. **Сгенерировать клиент** из `proto/brokapi/gateway/v1/gateway.proto` (он подключает `types.proto`) обычным для вашего языка инструментом (`protoc` с плагином gRPC или `buf`).
   Строки `option go_package` в файлах нет, чтобы не навязывать путь модуля. Нужен `protoc` 3.15 или новее (поля `optional` старые версии не собирают, проверьте `protoc --version`).
   Модуль для Go генерирует проверка `tools/proto-check` на каждой правке гейтвея (`tools/proto-check --write` записывает код в `go/gateway/v1`), она же показывает команду `protoc`.
2. **Подключиться** по адресу из `gateway.addr`. Адрес берите из файла, путь до сокета самим не собирайте, и читайте файл заново при каждом переподключении: перезапущенный гейтвей на Windows слушает уже на другом порту.
   Пока гейтвей перезапускается, файла нет (около полсекунды), а после его появления `Health` еще около секунды отвечает `STARTING`: читайте файл с повтором и паузой, затем ждите `Health = READY`.
   gRPC понимает адрес сокета Unix в виде `unix:/путь/к/сокету`. Шифрования нет: канал открытый, но локальный.
3. **Слать два заголовка** с каждым вызовом: `authorization: Bearer <ключ>` и `x-brokapi-bot: <имя>`.
4. **Соблюдать порядок**: открыть `Events`, дождаться кадра `Ready`, подписаться, вызвать `Reconcile`, торговать. Поток `Events` закончился - гейтвей остановился или
   перезапускается: пройдите шаги заново, начиная с чтения `gateway.addr`. Что при этом пропущено, скажет `Gap` ([События](events.md)). Поле `opts` в `SubscribeRequest`
   читает только `SubscribePortfolio`: у `SubscribeOrderState`, `SubscribeStopOrders` и `SubscribeExecutions` оно ни на что не влияет.
5. **Читать значения как договорено**: цена, количество и деньги - строки с десятичным числом (не `double`), время - целое число наносекунд в полях `*_ns`, `cid` - UUID
   с дефисами, который придумывает бот. Сравнивайте числа как десятичные, а не как строки: заявка по цене `"70.00"` может вернуться в событиях с ценой `"70"`.
6. **Разбирать ошибки** из двоичного заголовка ответа `brokapi-error-bin`: это сообщение `ErrorDetail`. Код статуса gRPC - подсказка общим инструментам, решает деталь.

Адрес `unix:/путь` из файла grpc-go принимает как есть, это проверяет тест бота на Go. Для других языков точное имя смотрите в документации gRPC (формат имен:
`github.com/grpc/grpc/blob/master/doc/naming.md`): на `grpcio` для Python это не проверялось (пакет `brokapi` для Python им не пользуется).

## Ошибки

Ошибка библиотеки приходит как статус gRPC с заголовком `brokapi-error-bin`. Код статуса показывает общий вид, настоящий вид - в поле `kind` детали.

| `kind` в детали | Код gRPC | Команда выполнялась? | Что делать |
|---|---|---|---|
| `CONFIG` | `INVALID_ARGUMENT` | нет | Исправить запрос или настройку. Повтор не поможет |
| `TRANSPORT` | `UNAVAILABLE` | для чтения неважно, для команды нет, если ответ потерян | Подождать и повторить чтение. Команду выясняйте через `OrderState` |
| `RATE_LIMITED` | `RESOURCE_EXHAUSTED` | нет | Подождать `retry_after_ns` и повторить |
| `REJECTED` | `NOT_FOUND` или `FAILED_PRECONDITION` | нет | Брокер отказал. Код отказа в поле `code` (`not_found`, `price_off_step`, ...) |
| `UNKNOWN` | `UNKNOWN` | **неизвестно** | Не повторять. Выяснить через `OrderState` и сверку: [Если что-то пошло не так](../rust/recovery.md) |
| `UNSUPPORTED` | `UNIMPLEMENTED` | нет | У брокера нет такой возможности, ее имя в поле `capability` |
| `NOT_RECONCILED` | `FAILED_PRECONDITION` | нет | Сделать `Reconcile` и повторить |
| `DEGRADED` | `ABORTED` | нет | Данные о заявках могли потеряться: `Reconcile` |
| `SHUTTING_DOWN` | `UNAVAILABLE` | нет | Гейтвей останавливается |
| `GATEWAY_STARTING` | `UNAVAILABLE` | нет | Гейтвей еще сверяет журнал. Ждать `Health = READY` |
| `BAD_REQUEST` | `INVALID_ARGUMENT` | нет | Запрос не разобран: плохой `cid`, плохое число |

Две ошибки не про брокера: `UNAUTHENTICATED` (нет заголовка с ключом или ключ чужой) и `INVALID_ARGUMENT` с текстом про имя бота (имя не из допустимых символов).
Значение каждой ошибки библиотеки: [Ошибки и что с ними делать](../errors.md).

**Потерянный ответ на команду.** Если гейтвей не ответил на команду (связь оборвалась, вышел срок), клиент возвращает `Unknown` и не повторяет вызов: гейтвей мог
команду выполнить. Если же гейтвей ответил отказом `GATEWAY_STARTING` или `BAD_REQUEST`, команда точно не выполнялась, и ее можно повторить.
